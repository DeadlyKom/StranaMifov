ФОРМАТЫ РЕСУРСОВ MYTHLAND, СТАТИЧЕСКИ ПОДТВЕРЖДЁННАЯ ЧАСТЬ

Границы подтверждения
Адрес загрузки в каталоге TR-DOS и адрес, фактически заданный загрузчиком, необходимо различать. Например, SOLDIERS имеет каталожный адрес #C700, но основной код #640B..#6411 читает его в логический банк 3 по #C000. Указанные ниже форматы основаны на конкретных потребителях. Одинаковая длина или говорящее имя файла сами по себе не подтверждают назначение поля.

SOLDIERS/C, слот 21, 1050 байтов
25 записей по 42 (#2A) байта. Внешний игровой ID отряда начинается с 1. Функция #8036 выбирает логический банк 3 и вычисляет IX=#BFD6+42*ID, то есть ID 1 соответствует #C000, ID 25 соответствует #C3F0. ID 0 недопустим для этого вызывающего кода, поскольку DJNZ выполнит 256 сложений.

Подтверждённые поля одной записи:
+#00..+#0B  Имя CP866, дополненное пробелами до 12 символов
+#0C        Нулевой терминатор имени в исследованном файле. Скрытый редактор #62D8 печатает запись с начала до нулевого байта
+#0D        Флаги. Основной код #883A переносит младшие три бита в поле +9 боевой записи. Игровое значение каждого из трёх битов отдельно здесь не устанавливается
+#0F        Базовый запас действий. Основной код переносит его в +7 боевой записи, #F578 восстанавливает из +7 текущий запас +12 на раунд
+#10        Начальное значение расходуемого боевого счётчика +8. Уменьшается в #D5BB. Название «число стрел» без дополнительного разбора не считается доказанным
+#13        ID замены отряда по первой ветви #9EF8..#9F18. Ноль означает отсутствие этой замены. Условие сравнивает служебный байт состояния отряда IY+25 с порогом описателя +#28
+#14        ID замены при деградации, читается #9F5B и используется #9F75. Ноль означает отсутствие замены
+#1A..+#1B  Little-endian 16-битная величина на одного воина. Боевая функция #F4A3 умножает её на численность, представленную пятибайтным числом ROM, и суммирует результаты пяти записей. Более узкое игровое название здесь не устанавливается
+#28        Порог первой ветви замены, сравнение #9F01
+#29        Порог деградации, сравнение #9F64. Скрытый редактор изменяет только этот байт каждой записи через #6355..#63B9

Смысл +#29 дополнительно описан собственным HELPG.tx игры: это число дней без боя до утраты квалификации. Скрытый редактор принимает байт с арифметическим переполнением по модулю 256, шаги управления +1, -1, +10, -10.

Отдельное расхождение документации и кода: HELP утверждает, что нулевой индивидуальный счётчик отключает деградацию. Однако видимая ветвь #9F5B..#9F67 проверяет на ноль только ID замены (+#14), затем сравнивает текущий счётчик с +#29 и пропускает деградацию только при CF=1. При +#29=0 и ненулевом ID замены CF=0 для любого беззнакового текущего счётчика, поэтому эта ветвь не пропускается. Это локальный статический результат; поведение конкретной пользовательской конфигурации в игре не проверялось. Нельзя подменять алгоритм заявлениями HELP. У простолюдинов нулевому порогу соответствует одновременно нулевой ID замены.

Остальные поля +#0E, +#11..+#12, +#15..+#19, +#1C..+#27 сохраняются как исходные байты. Их окончательные игровые названия этим документом не назначаются.

Переключатель деградации в head.co/C
Это изменение кода, а не независимый флаг состояния. Редактор читает сектор со смещением #3E в #7C38. Байт #7C41 находится в файле по смещению #3E09, что для head.co с ORG #615E соответствует адресу #9F67. Исходные два байта #38, #5F — JR C, #9FC8. Переключение первого байта на #18 превращает их в безусловный JR, #9FC8, обходящий ветвь деградации. При #18 меню пишет «отключена», при #38 — «включена». На диск при сохранении пишется полный сектор, с сохранением остальных байтов сектора.

Служебные счётчики по ID отряда
Основная функция #7AA4 возвращает IX=#6A72+ID. #9EDC увеличивает байт +0 в ходе обработки армии. Первая ветвь замены #9EFE читает по тому же указателю +25, ветвь деградации #9F61 читает +0. #7A94 сбрасывает оба байта +0 и +25. Счётчики образуют два параллельных массива по ID, а не полноценные структуры с шагом 26.

Состояние армии игрока
Основной код #9EE4..#9FCE обходит пять записей от #6A1E с шагом 3. Первый байт — ID отряда, ноль завершает обход. Два следующих байта трактуются как исходное 16-битное количество при создании боевых записей. Семантику отдельной таблицы служебных состояний IY здесь следует отличать от этих трёхбайтных записей.

Боевая запись, шаг 18 (#12) байтов
Временная структура создаётся основным кодом #883A и обрабатывается модулем bitwa.co.
+0      ID отряда, 0 означает пустую запись
+1      Служебное поле, назначение не установлено
+2..6   Пятибайтная численность/величина, используемая калькулятором ROM ZX Spectrum
+7      Базовый запас действий на раунд
+8      Расходуемый счётчик, уменьшается #D5BB
+9      Флаги, биты 0..2 из SOLDIERS+#0D, бит 3 отметка текущего прохода, бит 7 результат численной проверки #F62D
+10     C, столбец 0..7
+11     B, строка 0..4
+12     Оставшийся запас действий в текущем раунде
+13     Эффект, младшая тетрада длительность, старшая сохраняется при уменьшении
+14..15 Исходное 16-битное количество из записи армии
+16..17 Назначение не установлено

Стратегические карты KARTA1..KARTA4
Каждый файл содержит 16100 байтов. Основной код #80AE выбирает логический банк 10, #80B4 вычисляет HL=#C000+161*B+C. #80C4 читает байт карты с сохранением выбранного ранее банка. Деление длины файла на шаг 161 даёт 100 строк по 161 столбцу. Это байтовая сетка, а не готовая экранная картинка. #63EA..#63F1 устанавливает бит 7 текущей клетки при запуске. Для оставшихся семи битов этого документа недостаточно, чтобы назначить все значения ландшафта и объектов.

Боевая маска препятствий
Модуль bitwa.co использует #FCE8..#FCEC, пять байтов на поле 5 строк по 8 столбцов. Адрес байта #FCE8+B, бит 7-C. Помощники #E013, #E018, #E01E, #E023 обслуживают проверки/изменения этой маски. Это рабочий буфер боя, не отдельный 16100-байтовый ресурс карты.

IP1..IP8, слоты 36..43, каждый по 144 байта
Подтверждённый портрет 32x32 пикселя с атрибутами. Основной код #63A1..#63AF выбирает имя IP? и читает файл в логический банк 4 по #EF30. Процедура #957C..#9599 вызывает вывод #7545 с DE=#0404, то есть 4x4 знакоместа.
Смещения 0..127 — пиксельные данные. В каждом из четырёх горизонтальных рядов знакомест хранятся восемь строк по четыре байта. Формула файлового смещения пиксельного байта: floor(y/8)*32+(y mod 8)*4+floor(x/8).
Смещения 128..143 — 16 атрибутов, четыре строки по четыре атрибута. Формула: 128+floor(y/8)*4+floor(x/8).
Потребитель #7545 сначала копирует пиксели с учётом нелинейного экранного адреса, затем линейные атрибуты.

DATA1/C, слот 46, 3643 байта, runtime банк 3: #C41A
Основной код #6414..#641A задаёт этот адрес явно. Подтверждены две таблицы внутри ресурса:
1. #804E вычисляет IX=#CCAF+28*ID, первый допустимый ID 1 даёт #CCCB. Это смещение #08B1 от начала DATA1, шаг #1C. Игровое назначение всех полей не установлено.
2. #8066 вычисляет IX=#CE58+23*ID, первый ID 1 даёт #CE6F. Это смещение #0A55 от начала DATA1, шаг #17. Игровое назначение всех полей не установлено.
Размеры таблиц и конечный допустимый ID нельзя устанавливать только по расстоянию до следующей таблицы без разбора потребителей.

PERSON1..PERSON8
Файлы содержат персональные начальные данные с русским именем в начале, что видно по байтам: PERSON1 «Принцесса», PERSON7 «Наемник». В первых девяти байтах находится поле имени, байт +9 нулевой в исследованных файлах. Семь файлов имеют длину 245, PERSON7 имеет длину 270. Адреса в каталоге образуют последовательный диапазон #8000..#87C0 с учётом фактических длин.
Это не восемь одинаковых по размеру записей: нельзя нормализовать PERSON7 до 245 байтов, отбрасывать последние 25 или добавлять их другим файлам. Назначение числовых полей после имени здесь остаётся неустановленным до связывания с потребителями и глобальными переменными.

WERWOIN1..WERWOIN3
Три файла по 2000 байтов, суммарно 6000. Каталожные адреса #8000, #87D0, #8FA0 образуют последовательный диапазон. В начале WERWOIN1 видна повторяемая последовательность вида 01 28 14 00 0A 00, 02 32 0A 00 05 00 и далее. Одно это наблюдение не доказывает шестибайтную структуру всего ресурса: 2000 не делится на 6. До установления потребителя нельзя назначать этим байтам названия вроде координат, количества или цены.

MGPOWER1..MGPOWER3
Длины 110, 115, 110 байтов, каталожные адреса #8000, #806E, #80E1. В сумме 335 байтов. Они делятся на 5, но без потребителя это не доказательство единой пятибайтной записи. Игровая документация описывает магические силы и заклинания, однако не связывает конкретные поля файлов с расходом, ценой и эффектами. Такие названия здесь сознательно не назначаются.

HELPG.tx/C
Слот 52, длина 23799 (#5CF7), загрузка #7724. Содержимое зашифровано с участием R. Код #6218 инициализирует R как XOR физического номера сектора и трека файла. Для этого образа сектор 15 (#0F), трек 72 (#48), начальное R=#47. Длина берётся из дескриптора #5CE8.
Точный цикл #6227..#6235 эмулирован до #6237, результат сохранён help_decoded.bin. Печатаемые знаки декодируются CP866, CR=#0D означает перевод строки, нулевой байт завершает страницу. Полученный HELP содержит авторское описание игры и вступление STARS OF KELADAN. Геймплейные утверждения HELP — свидетельство авторов текста, а не подтверждение конкретного алгоритма двигателя.

HERTXT и TEXT
Файлы являются CP866-текстом с возвратами каретки и служебными байтами. Их каталоговые длины и исходные байты сохраняются. Нельзя удалять нули и управляющие коды в файлах, используемых движком, только ради удобства чтения.

Графические ресурсы HERIMG, SPR1..SPR3, STROENIA, PRES
В этом документе не назначается общий формат по имени. Определение bitmap, маски, атрибутов, кадров и размеров требует конкретной процедуры вывода. Формат IP выше подтверждён отдельно и не распространяется автоматически на остальные графические ресурсы.

Сохранения .M
Активный DEADLY/M и удалённые записи имеют одинаковую логическую длину 35584 байта. Значения могут храниться с инверсией байтов, но полную схему сохранения и связи с файлами PERSON нельзя выводить из совпадения отдельных строк или размера. Исходная полезная длина, секторный хвост и удалённая запись каталога должны сохраняться отдельно.

Пять битов ввода скрытого меню
Скрытая процедура #6B40 объединяет состояния нескольких раскладок клавиатуры и Kempston. Итог C: бит 0 действие, бит 1 вниз, бит 2 вверх, бит 3 вправо, бит 4 влево. Таблицы #6C5F..#6C72 содержат четыре группы по пять упакованных кодов кнопок, #6C4D..#6C5E — девять 16-битных портов. Эти данные относятся к сервисному меню, а не автоматически ко всем игровым модулям.

Отдельная маска открытия стратегических карт
O13: #B48E выбирает банк 11 и проверяет бит в #C000+(map_id-1)*2100+row*21+floor(column/8), бит 7-(column mod8). Размер континента 100 строк*21 байт=2100, четыре континента 8400 байтов. В последнем байте строки используется только часть битов, поскольку карта имеет 161 столбец. Именно эта маска управляет картой пройденного, поэтому бит 7 основного 16100-байтового массива нельзя называть маской открытия по одному факту его установки. O13 рисует её фрагментами 42x26 клеток по 4x4 пикселя.

Таблица замков, банк 0: #C000
Основная процедура #87D1 перебирает 80 записей с шагом 35, а O17: #B5E9 выбирает собственные замки. Подтверждённые поля: +0 бит 0 пропускает запись, +1 столбец, +2 строка, +3..+17 имя 15 байтов, +19 владелец, +20..+34 пять троек ID и 16-битное количество гарнизона. Владелец 0 означает собственный замок, #FF используется как особое отсутствие владельца/разбойники, ID1..15 связываются с описателями врагов. Указатель #867B и большинство интерфейсных процедур указывают на имя, то есть начало физической записи плюс 3. Нельзя перепутать +17 от имени с +17 от физической записи: гарнизон находится имя+17=запись+20. O21 позволяет менять все 15 байтов имени и переносить численность между гарнизоном и армией.

Два описателя в DATA1 теперь связаны с семантикой
O17: #B6D8 перебирает ID1..15, использует #804E и печатает имена побеждённых врагов. Следовательно, таблица с первым элементом #CCCB и шагом 28 содержит их описатели. O17: #B8F3 перебирает ID1..10, проверяет изучение заклинаний в #6A0A..#6A13, использует #8066 и печатает имена. Таблица с первым элементом #CE6F и шагом 23 содержит описатели 10 заклинаний. Все числовые поля по-прежнему требуют индивидуальных потребителей, эти имена не распространяются на неизвестные смещения автоматически.

Карта цели
O15: #B200 считает 25 открытых частей в #6A55..#6A59, по 5 бит на строку. Сами 25 байтов узора находятся #6A5A..#6A72. O16: #B200 сравнивает младшие 6 бит этих байтов с квадратом 5x5 стратегической карты вокруг героя. Это сравнение игнорирует служебные биты 6/7. O15 отображает каждую клетку 32x32 пикселя по формату 128 пиксельных байтов+16 атрибутов из банка 4: #C000+144*(тип AND #3F); бит 6 включает горизонтальное отражение. Вне открытой части рисуется заглушка банк 4: #EEA0.

Шестибайтовые записи отрядов на карте
O21: #B801 получает таблицу из дескриптора #6B69 текущего континента, шаг 6. В +0 хранит флаги, бит 0=1 используется как свободная запись. В +1/+2 записывает столбец/строку, в +3 ID отряда, в +4/+5 число. Это подтверждает именно эти записи и их потребителя, но не позволяет без загрузочного маршрута отождествлять всю таблицу с WERWOIN1..3.

Поведение экрана поражения
O20: #B200 переносит имя KB.co/C из #6CDD в #5CDD, вызывает TR-DOS C=#0E, A=0, затем JP #6149. Следовательно, на этой ветви загружается стартовый блок. Основания описывать данный вызов как удаление сохранения отсутствуют.

NAZWANIE/C и уникальные имена
Длина 3200 байтов раскладывается 80*16+160*12. Это разбиение подтверждено BL3: #77A3 и его вызовами: #686B передаёт шаг 16, число 80, указатель перед первым именем #BFF0, а #68F9 шаг 12, число 160, указатель #C4F4. Первая таблица начинается банк 1: #C000 и имеет 80 записей по 16, вторая банк 1: #C500 и имеет 160 записей по 12. Первые 15 или 11 байтов записи копируются в банк 0, после них приёмнику дописывается 0. Последний байт исходной записи является флагом использования, при выборе ему присваивается #FF. При полном использовании таблицы явного аварийного выхода из поиска нового имени нет. Для замковой записи это подтверждает нулевой терминатор +18 после 15 символов имени +3..+17.

Весовые записи WERWOIN в фазе создания игры
BL3: #67C1..#67C7 читает выбранный WERWOIN? в банк 3: #CB1A. BL3: #78D0 использует 6-байтовую весовую запись: +0 ID отряда, +1 верхний порог случайного байта, +2/+3 little-endian базовое количество, +4/+5 масштаб случайной добавки. Количество равно база+randomScaled(масштаб). Таблицы выбираются по исходной базе HL+150*A, затем поиск идёт с добавлением 6 до нужного порога. Для гарнизонов вызывающая база HL=#CD9E, для другой группы армий HL=#CFF6. Функция генерирует 2..5 трёхбайтовых отрядов и сама не очищает оставшиеся слоты. Следовательно, 6-байтовый формат относится к доказанным участкам весовых таблиц, а не применяется автоматически ко всем 2000 байтам файла.

Дополнительные поля SOLDIERS по BL3
В фазе BL3 файл находится банк 3: #C700, а не в итоговом runtime: #C000. Поэтому #7808 вычисляет описатель как #C6D6+42*ID. Поле +#12 сравнивается с входной категорией 1..4 при случайном выборе отряда, поле +#20/+#21 задаёт 16-битную начальную численность создаваемой 6-байтовой группы. Эти поля подтверждены потребителем, но более узкие имена вроде «тип строения» без разбора соответствующих таблиц не назначаются.
